title: The app's API
description: The loopback API the desktop app and plugins use, and the box API behind it.
---

The desktop app is only a view. It talks to the laptop agent (`berth agent`,
which any `berth` command that needs it starts, and
`berth agent install` keeps running as a service), which holds the
connections to every box. When the agent isn't running, the app offers to
start it (**Start the Shipyard agent** runs `berth agent start`; ticking
**Start at login** runs `berth agent install`). Closing the app, or the app
crashing, never stops an agent session or a forward.

## Transport

The agent serves the app on `http://127.0.0.1:1378`.

- **Token.** Every request carries `Authorization: Bearer <token>`. WebSocket
  upgrades, which cannot set headers from a browser, pass `?token=<token>`
  instead; on any other request a query token is ignored, so it never lands
  in logs or history. The token is in `<state>/client/ui-token` (mode 0600); the Tauri
  shell reads it with the `ui_endpoint` command, which returns
  `{ "url": "http://127.0.0.1:1378", "token": "…" }`. For browser-only UI
  work, `berth ui-token` prints the same JSON.
- **Host check.** Requests whose `Host` is not `127.0.0.1:1378` or
  `localhost:1378` are refused, so a web page cannot reach the agent through
  DNS rebinding.
- **CORS.** Allowed origins are `tauri://localhost`, `http://tauri.localhost`,
  `https://tauri.localhost`, and `http://localhost:1420` to `:1439` (Vite in
  development). The token, not the origin, is what keeps other pages out.
- **Errors.** A failed request answers `{ "error": "…", "code": "…" }`. The
  message is for people and logs; branch on the code. The box's codes are
  `not_found`, `session_exited` (the session's program has ended, so it takes
  no input), `session_exists`, `agent_waiting` (sending now would answer its
  question), `refused` (a `before:` hook said no), `unsupported`, `tmux_missing`,
  `git_failed`, `command_failed`, `too_many`, `bad_request` and `internal`,
  and for [plugins' helpers](#boxes) `helper_off`, `helper_invalid`,
  `helper_mismatch`, `helper_missing` and `helper_unreachable`. The
  agent adds `box_unreachable` (the request never reached the box, 503, or may
  have, 502), `box_unknown` (no paired box by that name) and `box_outdated`
  (the box's berthd doesn't have that route yet). A request for a box the
  agent knows is offline is answered at once with 503 `box_unreachable` and
  `Retry-After` (seconds to its next try), rather than after a dial timeout.
  The app gives each read (`GET`, but not a `…/wait` long poll) 30 seconds
  and then fails it as `box_timeout` (504).

A box that isn't online carries `retry_at` (when the agent tries it next) and `attempts` (failed tries in a row). `link` says how well it is reached: `slow` (still online; requests go through) and `reason`, the recent `max_ms` and `jitter_ms`, and `path` (`via`: `direct`, `relay` with `relay` and `relay_name`, or `peer-relay`) when Tailscale can tell |

| `DELETE /v1/marketplace/{id}` | `{ removed }`: deletes a plugin the listing installed, and the permission it had. 409 `plugin_by_hand` for any other plugin |
| `GET /v1/plugins/{id}/helper?box=B` | `HelperStatus`: [the plugin's helper](/docs/guides/plugins#give-a-plugin-a-helper) on that box. `{ plugin, box, state, platform, version?, latest?, update?, error?, attached? }`, where `state` is `none` (the plugin has no helper), `unsupported` (it has no build for the box's `platform`, or the box's berthd cannot run helpers; `error` says which), `off`, `installing`, `starting`, `running` or `failed` (`error` says why; berthd keeps trying). `platform` is the box's, as `linux-arm64` (empty when the box was not asked); `version` is what the box runs, `latest` what the plugin's manifest names, and `update` says they are not the same helper. Only for a plugin that is installed and allowed as it is now: otherwise 409 `plugin_not_installed` or `plugin_not_allowed`, and 409 `helper_invalid` when its manifest's helper cannot be used |
| `POST /v1/plugins/{id}/helper?box=B` | → `HelperStatus`. Installs the helper on that box, or brings the one there up to the manifest's, and turns it on: the agent downloads the build for the box's platform from the manifest's address, checks its size and SHA-256 against the manifest, and uploads it to the box over Shipyard's own connection, so the box needs no way out to the internet. It answers once the helper is up, or has failed to come up. Asking for what already runs does nothing. The same 409s as `GET`, and: 409 `helper_none` (the plugin has no helper), 409 `helper_unsupported`, 409 `helper_busy` (it is being installed there already), 502 `helper_download` (the build could not be fetched) and 502 `helper_mismatch` (it is not the bytes the manifest names; nothing was uploaded). A refusal of the box's comes back with the box's status and code |
| `DELETE /v1/plugins/{id}/helper?box=B&purge=1` | → `HelperStatus`. Stops the helper on that box and removes its program. Its data stays for the next time unless `purge=1`. The answer's `attached` lists the services running on the box that were started with what the helper answered (`{ location, worktree, service }` each): they still point at the helper, and need restarting. This one does not ask that the plugin be allowed, or installed: a plugin you turned off can still have its helper taken away |

| `POST /v1/team/{org}/retry` | `{ box?, from? }` → `TeamStatus`: start again from a step or a project (default: the one that failed) |
| `GET /v1/team/{org}/update` | `{ update }`: `null`, or a newer `.berth` commit than the one accepted: `from`, `to`, `author`, `commits`, `changes` (`kind`: add, remove or change; `area`: step, project, key or file; `sudo` on a step that newly asks for the password) and `sudo` (their titles). Nothing runs |
| `GET /v1/team` | the team setups this laptop accepted: `org`, `key` (the org or link it was read from), `id`, `name`, `commit`, `box`, `boxes`, `at`, and `status` (the box's `TeamStatus`) when the box is online |
| `GET /v1/hooks`, `PUT /v1/hooks` | the laptop's `hooks.json`: `{ path, hooks }`; PUT takes `{ hooks }` and announces `hooks.changed` |
| `GET /v1/queue` | `QueueItem[]`: prompts waiting for their box, oldest first |
| `POST /v1/queue` | `{ id?, box, session, text, wait?, enter? }` → `QueueItem`; the same `id` again returns the item already queued |
| `PATCH /v1/queue/{id}` | `{ box?, session?, text? }` → `QueueItem`: move or edit one; it goes back in line as `queued` |
| `POST /v1/queue/{id}/retry` | `QueueItem`: a failed one back in line |
| `POST /v1/queue/{id}/send` | `QueueItem` with `state` `delivered`, `failed` or `queued`: send it now, without waiting for the agent's turn; 409 while its box is offline |
| `DELETE /v1/queue/{id}` | the discarded `QueueItem`; 409 while it is being sent |

`QueueItem` is the offline prompt queue's entry ([the offline queue](/docs/guides/offline-queue)):

```ts
{ id, box, session, text, enter, wait, state, error?, created, attempts?, last_attempt?, blocked?, seq }
```

`state` is `queued` (waiting for the box),
`waiting` (the box is back; waiting for the agent's turn to end), `sending`,
or `failed` with `error`. `blocked` marks one held behind an earlier failed
prompt to the same session. `wait` (default true) holds a prompt while the
agent is mid-turn; `enter` (default true) presses Enter after it.

## Boxes

`ANY /v1/boxes/{box}/api/{path}` is passed to the box as `/v1/{path}`, query
string and body included, and the box's answer is streamed back. When the
box cannot be reached the agent answers itself: **503** when the request
never reached the box (safe to retry or queue), **502** when the connection
failed after it went out (the box may have acted on it). The box API:

`Session` carries the agent's state when an agent tool reports it:
`agent` (`claude`, `codex`, …) and `agent_state` (`idle`, `running`,
`waiting`, `finished`), plus `preset` (the agent preset it was started
with), `turn` (its current or last turn), `state_seq` and `fidelity`
(`hooks`, `partial` or `screen`), `queued` (prompts held until it is idle)
and, while it waits, `ask` (what its hooks said it asks for). `exited` is
true once the program has ended. `title` names the work: the first line of
the prompt it started with, or of the first prompt it was sent or typed, cut
to about 48 characters; `PATCH sessions/{name}` with `{ title }` renames it
(an empty title clears it). Only the title is kept, never the prompt.

A `Run` is `{ id, template, title?, status, steps, gate?, candidates?, usage?,
cursor?, params?, created, updated, finished?, error?, … }`, with `status`
one of `queued`, `running`, `waiting_gate`, `paused`, `succeeded`, `failed`,
`cancelled`, `interrupted`; `GET runs` lists summaries (the same without
`steps`). The info's `capabilities` lists `runs` and `exec.detach` on boxes
that have them.

A `Turn` is `{ id, session, agent?, n, origin?, sent_seq?, end_seq?, state,
queued?, started?, ended?, waits?, fidelity?, idem_key?, status? }`, with
`state` one of `queued`, `pending`, `running`, `waiting`, `finished`,
`exited`, `lost`; see [turns](/docs/concepts/sessions-and-agents#turns).

`GET locations/{name}/config` and `GET env` return secret references as
written, never their values.

## Terminals

`GET /v1/boxes/{box}/sessions/{name}/attach?cols=C&rows=R&token=T` upgrades
to a WebSocket.

- Box → app: binary messages, raw terminal output.
- App → box: binary messages are keystrokes; text messages are JSON
  `{"type":"resize","cols":C,"rows":R}`.

Closing the socket detaches; the session keeps running on the box. Attaching
again redraws the screen, so the app reconnects after sleep or a network
change by opening a new socket. When the [route](/docs/concepts/laptop-agent#routes-to-a-box)
the terminal rides goes down, the agent attaches again over another inside
the same socket: the screen is redrawn, and keys that may not have reached the
box are sent again first.

## Events

```json
{ "type": "agent.waiting", "time": "…", "box": "devl", "origin": "claude",
  "data": { "path": "/home/me/work/shop-checkout", "agent": "claude", "session_id": "…" } }
```

The app reacts to most box and laptop events: connections (`box.*`),
locations and worktrees (`location.*`, `worktree.*`, `service.*`), sessions
and agents (`session.*`, `agent.*`, `task.created`, `preview.open`),
automation (`flow.*`, `guard.acted`, `config.changed`, `hooks.changed`),
kits, team setups (`team.*`), shares, forwards, units, the queue (`queue.*`, never the prompt) and
secrets (`secret.*`, never a value). [Events and gates](/docs/reference/events)
lists every type and its data.
